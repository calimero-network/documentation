Five steps, from nothing to a running app you call from the terminal. The app is the KV Store, the apps repository's
reference app: a string key-value store.

## Before you start

- **Linux** (x86_64 or aarch64) with glibc 2.35 or newer (Ubuntu 22.04, Debian 12 and later), or **macOS** on Apple
  silicon.
- **[Docker](https://docs.docker.com/get-docker/)**, installed and running: the local cluster runs in the release's
  Docker image. On Linux, your user must be able to run `docker` (in the `docker` group); on a Mac, start Docker
  Desktop.
- **`curl` and `git`.**
- **Rust**, from [rustup](https://rustup.rs), with the WebAssembly target the build uses:

  ```bash
  rustup target add wasm32-wasip2
  ```

Then install `meroctl`, the command line. The installer checks it against the release's `SHA256SUMS` and puts it in
`~/.local/bin`:

```bash
curl -fsSL https://raw.githubusercontent.com/calimero-network/core/master/scripts/install.sh | sh
```

Put `~/.local/bin` on your `PATH`, now and for every new terminal:

```bash
brew install calimero-network/tap/meroctl
```

## Five steps

<Steps>

1. **Run a node.**

   ```bash
   meroctl local up
   ```

   This starts `merod local`, the node, in the release's Docker image, in the background: a development cluster of
   three nodes on `http://127.0.0.1:2501`-`2503`, in one container, ready in a few seconds (the first time, after
   Docker pulls the image). It keeps its state in
   `~/.calimero/meroctl/local/`, saves the cluster as the `meroctl` node `local`, and prints the node URLs and an
   operator token. `meroctl local down`, from any directory, stops it; the state stays for the next `up`.

2. **Clone an app.**

   ```bash
   meroctl app new my-app && cd my-app
   ```

   `app new` starts a project from the [apps repository](https://github.com/calimero-network/apps)'s `kv-store` app:
   the app, the shared `packages/` and `scripts/` it builds with, and the root files that pin their versions, in a new
   git repository with one commit:

   ```text
   my-app/
   ├── Cargo.toml  README.md  package.json  pnpm-*  tsconfig.base.json
   ├── apps/kv-store/
   │   ├── logic/    the app: a Rust crate
   │   └── app/      its frontend
   ├── packages/     shared frontend packages
   └── scripts/      component-build.sh: build the app and write its ABI
   ```

3. **Build it.**

   ```bash
   meroctl app build apps/kv-store/logic
   ```

   This compiles the crate for `wasm32-wasip2` into a `calimero:app` component, with the app's ABI (its methods,
   events and types) embedded, and writes `apps/kv-store/logic/app.component.wasm`. The first build fetches and
   compiles the SDK and takes a few minutes; after that, about 30 seconds.

4. **Deploy it.** Sign up first:

   ```bash
   meroctl login --dev-passkey ~/.calimero/me.json --name me
   ```

   ```json
   { "accountId": "…", "passkey": "/home/you/.calimero/me.json" }
   ```

   People sign in to Calimero with passkeys. A development cluster also takes a passkey kept in a file, so you can sign
   in from a terminal: when `me.json` does not exist, `meroctl` creates a new passkey (a software one, made the way a
   phone or security key makes one), signs up an account named `me` with it, and saves it in the file, readable only by
   you. Next time, the same command signs in with it. The file is your development account: keep it out of your
   project (here it lives in `~/.calimero`), and delete it to start over with a new account. A real cluster refuses a
   file passkey; there you sign in with a real one, or use an API key from the console.

   Then create an instance of the app from the component:

   ```bash
   meroctl context create --name kv --path apps/kv-store/logic/app.component.wasm --alias kv
   ```

   ```json
   { "appId": "…", "contextId": "…", "group": 2, "replicas": [1, 2, 3], "compute": false }
   ```

   `meroctl` calls an app instance a *context*. The instance runs on all three nodes (`replicas`), with its own log.
   Its `init` ran once, as you, and it lives in your personal organization, which the sign-up made. `--alias kv` names
   it for your account.

5. **Call it.** A call writes; the cluster's leader for the instance runs it and appends it to the log:

   ```bash
   meroctl call --context kv set --args '{"key":"a","value":"1"}'
   ```

   ```json
   {
     "index": 3,
     "result": null,
     "events": [{ "kind": "Inserted", "data": { "key": "a", "value": "1" } }],
     …
   }
   ```

   `index` is the log index the call committed at, and `events` what it emitted. A view reads without writing:

   ```bash
   meroctl call --context kv get --args '{"key":"a"}' --view
   ```

   ```json
   { "index": 3, "result": "1", "receipt": { … } }
   ```

   The receipt is the answering node's signature over the result, under a key its attestation binds.

</Steps>

That is the whole loop: a node, an app, a build, an instance, a call.

## Without Docker

`meroctl local up --local` runs the `merod` binary from your `PATH` instead of the image. Install it with
`... | sh -s -- merod meroctl` (Linux, and macOS from core 1.0.0-rc.25) or `brew install calimero-network/tap/merod`.

## With 1.0.0-rc.24

Three differences in the release before 1.0.0-rc.25:

- `meroctl local up` runs the `merod` on `PATH` unless you pass `--docker`, and macOS has no `merod`: there, use
  `meroctl local up --docker`.
- It keeps its state in `.merod-local/` in the directory you ran it from, so run `meroctl local down` from that
  directory.
- `meroctl app build` with a path, as in step 3, also leaves an empty `apps/kv-store/logic/apps/` directory behind;
  delete it.

<Aside type="caution" title="A development cluster is not a real one">
`meroctl local up` runs with mock attestation and a development storage key, and accepts file passkeys and raw
components (`--path`). Clients trust it only when told to (`meroctl local up` saves it that way; `allowMock: true` in
mero-js), never by default. A real cluster sends real TDX quotes, signs people in with real passkeys, and installs
only signed packages from a registry: see [Package & publish](/guide/publish/).
</Aside>
